# Changelog

All notable changes to TetriZZ are listed here, newest first.

## Unreleased

- Player identity: a page now makes a secret key that stays in the browser, and its player id is derived from it. TetriZZ's own server checks the proof on every connection (`hello`) and on every `/api/v1` request, so nobody can take another player's seat or the host role, and nobody can erase or silence another player's stored data just by knowing their id. Online ids change once, to 32 hex characters, and `tetris_pid` is gone. The server answers 403 `identity` to a wrong key, `tetrizz_api_refused_total{reason="identity"}` counts them, and the key is never stored or logged. Pages from before this change are refused by the own server and play on the other backends. See `docs/SERVER.md`, "Who a player is".
- The old "a modern guideline Tetris" description is gone: the page's `description` and `og:description` tags and the manifest now describe TetriZZ as a fast, competitive Tetris game. Text only; nothing else changes.
- Fixed the VPS stack: Caddy's `/config.json` told the page its server was at `/ws`, and the page adds `/ws` itself, so it opened `/ws/ws`, which Caddy does not forward. The page then quietly fell back to the public relay and never reached the own server. `config.json` now says `"/"` (the page's own address). A test reads the Caddyfile and follows the address the way the page does, and a browser check opens the built page through a real Caddy in front of the built server and requires its socket at `/ws`.
- Hosting guides and files for the static hosts: `docs/DEPLOYMENT.md` now covers GitHub Pages, Vercel, Cloudflare Pages, the VPS stack and a static page with a server of your own. `.github/workflows/pages.yml` publishes to GitHub Pages (repository variables carry the optional network settings), `vercel.json` holds the Vercel build and headers, and `deploy/cloudflare/_headers` is an optional headers file for Cloudflare Pages. The build was served under a sub-path and opened in Chromium to check that a project site works.
- The server can be run on a VPS with Docker. `compose.yaml` starts Caddy (TLS, the page, the socket on `/ws`, `/healthz`, never `/metrics`) and the room server with SQLite; `compose.postgres.yaml` swaps in PostgreSQL; `compose.monitoring.yaml` adds Prometheus, Grafana (three dashboards: overview, live, health), Loki and Alloy for logs, and a node exporter, with alert rules and their tests as files. Everything that must survive is under `./data`. `scripts/backup.sh` makes checked copies of the live database (7 daily, 4 weekly, optional rclone upload), `scripts/restore.sh` puts one back safely, `scripts/healthcheck.sh` is for cron. `docs/DOCKER.md` explains it. The Docker parts were checked with each vendor's own validators and a live Caddy in front of the built server; running the containers is left to the new CI jobs.
- The server looks after its own database and can tell its owner what is going on. A maintenance job rolls up today every few minutes and the last days every hour (late uploads from offline pages are counted), deletes rows past their retention, gives the space back and watches `DB_MAX_MB`: at 80 % it warns, over 100 % it halves every retention until the database fits. `/metrics` (off by default, `METRICS=on`; answered only with a bearer token or to a request that did not come through a proxy) lets Prometheus read connections, rooms, refusals, the heartbeat round trip, the API and telemetry counters, database size and rows, the maintenance jobs and today's games by mode. Telegram and Discord messages are sent for a start, a daily digest of yesterday, a failing database or job, the size budget, a slow event loop and bursts of errors, each with a cooldown. New settings are in `docs/SERVER.md` and `apps/server/.env.example`. The page is unchanged.
- The server can now keep what it learns about play. With `DB_DRIVER=sqlite` or `postgres` it opens the database at start and answers `/api/v1`: `POST /api/v1/telemetry` takes a batch of events, finished games, history lines, a session and a device description; `PUT /api/v1/players/<id>/telemetry` switches telemetry off or on for a player; `DELETE /api/v1/players/<id>` erases everything stored about a player. A page may retry freely (every item has an id the page made up), times are corrected for a wrong clock on the phone, events from a player who opted out are not stored, only the sender's own row of a game is stored, and no address is kept. Without a database (the default) nothing changes and `/api/v1` does not exist. New settings: `DB_DRIVER`, `SQLITE_PATH`, `DATABASE_URL`, `DB_SCHEMA`, `DB_POOL_MAX`, retention days, `DB_MAX_MB` and two limits (`docs/SERVER.md`). The page does not send anything yet.
- The server has a database layer, not connected yet: one repository interface over SQLite (Node's built-in `node:sqlite`) and PostgreSQL, numbered SQL migrations with checksums, tables for players, devices, sessions, games, raw events, player history and daily rollups, idempotent writes, rollups, purging that only touches days that were rolled up, and delete by player. The same tests run against both databases (and against PostgreSQL in CI). Nothing in the server uses it yet; the page and the room server behave as before.
- The own server exists: `apps/server` runs the room rules of `packages/protocol` (the reference model) on real WebSockets with Fastify. It checks the page's origin before the upgrade, limits sockets and messages per address and per connection, pings and cuts silent sockets, cuts pages that stop reading, stores room passwords as scrypt hashes, holds a dropped player's seat with real timers, answers `/healthz` and `/readyz`, and stops cleanly on SIGTERM. Settings are environment variables (`docs/SERVER.md`, `apps/server/.env.example`). Rooms live in memory only; there is no database, `/metrics` or Docker setup yet.
- Building the page with `--outDir` on the command line failed in the service worker step because that step looked in `dist`; both build plugins now follow the output directory. The default builds are byte-identical to before.
- Rooms on the own server: the host can change or remove the room password after the room is made (CHANGE PASSWORD is shown again for server rooms), and a player whose connection drops keeps the seat for a grace period (30 seconds by default, set by the server) instead of losing it at once. The seat keeps its role and ready flag, and the host keeps the host role; the page keeps trying to get back in for that time and shows the player as reconnecting to the others. Once the time is up the seat is removed and the host role passes on as before. The rules are in the protocol and its reference model; the real server is still to come.
- The page can now create and join rooms on TetriZZ's own server, once one is configured (`TETRIZZ_SERVER_URL` or `config.json`): under AUTO it is tried first, then Supabase, then the public relay, and the SERVER pick in Options offers it. The server holds the roster, the host and the password, so a wrong password, an unknown room or a newer version are the server's answers. Leaving, kicking, host change, ready and role swaps work as in relay rooms; if the connection drops in a lobby the reconnect panel is shown and the page joins again. Changing a room's password after it was made is not available on the server yet. A new browser check plays server rooms against a fake server.
- The wire protocol of the own server is written down and tested (`packages/protocol`: message types and parsers, and a reference model of the server's room rules), and the page has the client side of it: a socket module, a server Transport and a server RoomBackend. The protocol version helpers moved to their own file. A room request now carries the password the host typed, for backends that check it themselves.
- Online rooms now try the backends in the configured order (own server, Supabase, public relay) for both creating and joining, and Options has an Online group with a SERVER pick (AUTO or one backend to try first) that shows up when more than one backend is configured. The Supabase room channel's database-event handling moved out of the lobby into its own module with tests.
- Creating and joining an online room now go through the RoomBackend interface (`packages/protocol`): a backend answers with a result (room, host, seed and the host's rules, or a reason such as unknown room, password needed, newer version, no server reachable) and the lobby turns it into screens and notes, so the relay and Supabase code no longer touch the page. The relay join is now one awaited call that ends when the host accepts or refuses, the 9 second wait runs out or no broker answers. One small fix comes with it: when the MQTT library could not be loaded the JOIN ROOM button stayed on "JOINING ROOM…"; it is usable again. LAN rooms are still made by hand in the LAN panel. A new browser check covers the refusals of a relay join.
- Leaving a room, being kicked, handing the room to the next player and saving the ready flag now go through one RoomBackend interface (`packages/protocol`) with a relay, a LAN and a Supabase implementation and an in-memory room for tests. Behaviour is unchanged apart from two small cases listed in `docs/PROGRESS.md`. A new browser check covers leave, kick and host hand-over in a relay room.
- Network messages now go through one Transport interface (`packages/protocol`) with a LAN, a relay and a Supabase adapter and an in-memory one for tests. Incoming events are handled by one table per backend kind instead of three copies; which event each backend handles is unchanged. The host's `closed` message is now in the protocol's event list. A new browser check plays a relay room from lobby to match without a network.
- Online and LAN handshakes now carry a protocol version (`packages/protocol`): join, acknowledgement and the LAN hello announce version 1, and a message without a version counts as version 1, so this build and v1.2.0 can share rooms. A peer that announces a newer version is refused (relay rooms: the guest is told to reload; LAN: the host closes the connection). The message types sent over the relay and the event names are now written down as TypeScript types.
- Network settings moved out of the source. The Supabase address and key, the relay brokers and the two CDN libraries' addresses were written into the code; they now come from build environment variables (`TETRIZZ_SUPABASE_URL`, `TETRIZZ_SUPABASE_KEY`, `TETRIZZ_SERVER_URL`, `TETRIZZ_MQTT_BROKERS`) and an optional `config.json` next to the page, and the Content Security Policy and the service worker's no-cache list are generated from them. Without Supabase settings online rooms use the public relay and the Supabase library is not downloaded. The CDN libraries are pinned to exact versions (supabase-js 2.119.0, mqtt 5.16.1). The Supabase address and key were also removed from `legacy/`. See `docs/DEPLOYMENT.md`.
- While the tab was hidden (another window or browser in front), bots played at about 4 pieces per second whatever they were set to and the game clock ran at 0.82 times real time, so the PPS in the score panel sank the longer the tab stayed hidden. Bots now keep their pace and the game keeps real time while the tab is hidden.
- Bots now reach the pieces-per-second they are set to. Before, every piece was dropped up to one frame late and the delay added up, so a bot set to 10 PPS played about 8.8 to 9.3. Which moves a bot chooses is unchanged.
- Versus lobby: bot LEVEL and BOT PPS values typed in by hand are now saved (they showed but were not stored), and holding + or - on those two steppers repeats like the other steppers.
- Repository restructured as an npm-workspaces monorepo with a Vite build; the game itself is unchanged from v1.2.0.
- Page and service worker formatted with Prettier; unused functions and variables removed; all comments removed ahead of a rewrite. Behaviour and appearance are unchanged.
- Stylesheet moved out of the page into 25 ordered files under `apps/web/src/styles/`; nine unused CSS classes and their rules removed. Behaviour and appearance are unchanged.
- The page script is split into ES modules under `apps/web/src/` (36 feature modules and 23 ordered startup files) with per-module state objects, a typed event bus, a storage layer with schema versioning and migrations, a logger in place of silent error handlers, and a shared HTML escape helper applied to player names, room ids and replay titles. Gameplay is unchanged.
- Game rules (collision, kicks, spin detection, scoring, garbage maths, level tables, piece bag) moved into `packages/core` and are used by the solo game, the versus stations and the bots; the three separate rotation routines became one. The two bot evaluators share their board helpers. Random numbers and clocks can be replaced for tests. Behaviour is unchanged and checked against v1.2.0 on 2,749 recorded cases.
- Bot code moved into `packages/bot`; bots can plan in Web Workers (`tetris_botworker` setting, automatic by default) and fall back to planning on the page if workers are unavailable or stall.
- Bot planning is about 2.6 times faster.
- Slow frames are simulated in steps of at most 50 ms (up to 250 ms per frame), so the game keeps real time on slow devices instead of running slow.
- Board drawing no longer creates a new canvas for every board on every frame (the settled-blocks layer cache never worked; 1,120 canvases in 10 s of a 4-player match became 10).
- A hidden debug overlay with frame times and bot thinking figures: tap the version label five times to show or hide it.
- Quality drops automatically when frames stay slow (fewer clear particles, no floating background, then no particles or board bounce) and comes back when they are fast again; `tetris_adaptive=0` turns it off.
- Options has a new Motion group: REDUCE MOTION (auto follows the device setting, or on, or off) and ADAPTIVE QUALITY (on or off). Both are saved with SAVE and revert on cancel like the other options.
- The main menu footer shows the app version.
- The service worker of the multi-file build now pre-caches the built script and stylesheet and uses one cache per build.
